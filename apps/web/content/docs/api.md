The FlowForge API is a JSON-over-HTTP service. Clients use it to register workflows, start and inspect runs, and follow execution events; workers use it to lease tasks and report results. The TypeScript SDK wraps the endpoints most integrations need (see [Workers](/docs/workers) and [Workflow definitions](/docs/workflows)), but every operation is available over plain HTTP.

## Base URL

The API listens on `API_HOST`:`API_PORT` (default `127.0.0.1:4000`). Every endpoint on this page except the health checks lives under the `/v1` prefix:

```http
GET http://localhost:4000/v1/runs
```

The web app forwards `/api/*` to the API, so a browser on the web app's origin reaches the same endpoint at `/api/v1/runs`. SDK clients and workers can use either address as `apiUrl`: the API's own URL inside your network, or the web app's origin followed by `/api` (the developer page in the dashboard shows that form, and it works for long-polling workers too).

Request and response bodies are JSON. Timestamps are ISO 8601 strings in UTC (for example `2026-11-06T10:15:00.000Z`). IDs are UUIDs, except event and scheduling-decision IDs, which are integers.

## Authentication

### API keys

Send an API key as a Bearer token:

```http
Authorization: Bearer ffk_AbCdEf12_<43-character secret>
```

Keys have the form `ffk_<8-character id>_<43-character secret>`. The API stores only a SHA-256 hash, so a key is shown once, when it is created. Create keys from the dashboard (workspace owners and admins) or with the operator CLI:

```sh
node apps/api/dist/admin.js create-key <tenant-slug> <name> read,runs:write
```

A missing, malformed, unknown, revoked or expired key gets `401 unauthorized`. Every key belongs to one tenant (workspace), and every request is scoped to that tenant: IDs from another tenant answer `404`.

### Scopes

Each key carries one or more scopes. A request without the scope its endpoint needs gets `403 forbidden` with the message `Missing scope <scope>`.

| Scope | Grants |
| --- | --- |
| `read` | Every `GET` endpoint under `/v1` except the API key list, including `GET /v1/stream` |
| `workflows:write` | `PUT /v1/workflows` |
| `runs:write` | `POST /v1/workflows/{name}/runs`, `POST /v1/runs/{id}/cancel`, `POST /v1/tasks/{id}/retry` |
| `worker` | The worker protocol: `POST /v1/workers`, `POST /v1/workers/{id}/poll`, `POST /v1/workers/{id}/heartbeat`, `POST /v1/workers/{id}/deregister`, `POST /v1/tasks/{id}/complete`, `POST /v1/tasks/{id}/fail`, `POST /v1/tasks/{id}/checkpoint` |

Give each process the narrowest key it needs: a worker needs only `worker`; a service that starts runs needs `runs:write` (and `read` to poll for results).

The API key endpoints (`GET /v1/keys`, `POST /v1/keys`, `POST /v1/keys/{id}/revoke`) accept no API key at all, whatever its scopes: they require a signed-in dashboard user with the `owner` or `admin` role, so a leaked key cannot mint more keys.

### Dashboard sessions

When a request has no `Authorization` header, the API looks for a dashboard session cookie (`ff_session`, or `__Host-ff_session` on HTTPS deployments). Sessions come from Google or GitHub sign-in. A signed-in user's role maps to scopes:

| Role | Scopes |
| --- | --- |
| `owner`, `admin`, `member` | `read`, `workflows:write`, `runs:write` |
| `viewer` | `read` |

No role grants `worker`; workers always use API keys. Every session request other than `GET`, `HEAD` and `OPTIONS` must send the session's CSRF token in an `x-csrf-token` header, or it gets `403 csrf_failed`. The token is in the `ff_csrf` cookie (`__Host-ff_csrf` on HTTPS) and in the `csrfToken` field of `GET /auth/me`. See [Security](/docs/security) for sign-in, session lifetime and cookie details.

Independently of the credential, a request that carries an `Origin` header other than `APP_URL` or an origin listed in `ALLOWED_ORIGINS` is refused with `403 origin_not_allowed` unless it is a `GET` or `HEAD`. Server-side clients that send no `Origin` header are not affected.

## Errors

Every error response has the same envelope:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "Request validation failed",
    "details": {
      "issues": [{ "path": "limit", "message": "Too big: expected number to be <=100" }]
    },
    "requestId": "6f1c2b9a-3d4e-4f50-8a61-7b2c3d4e5f60"
  }
}
```

`code` is stable and meant for programs; `message` is for people. `details` is present only for some codes. `requestId` is generated by the API for each request; include it when you report a problem.

| Status | Code | When |
| --- | --- | --- |
| 400 | `invalid_request` | A path parameter, query parameter or body failed validation (`details.issues` lists each problem as `{ path, message }`), a cursor is malformed, or you asked to retry a task that is not `failed` |
| 400 | `invalid_request` | The request contains text the database cannot store: a NUL character (`\u0000`) or an unpaired UTF-16 surrogate, in any string or object key of the path, query or body. Also a body nested more than 100 levels deep. The message says where, for example `Request body.input.items[1].note contains a NUL character (\u0000)` |
| 400 | `fst_err_ctp_invalid_json_body` | The body is not valid JSON but `Content-Type` is `application/json` |
| 400 | `fst_err_ctp_empty_json_body` | `Content-Type` is `application/json` but the body is empty. Omit the header on `POST` requests that have no body |
| 401 | `unauthorized` | No credential, or the credential is malformed, unknown, revoked or expired |
| 403 | `forbidden` | The credential lacks the endpoint's scope or role |
| 403 | `csrf_failed` | A dashboard session made a write without a valid `x-csrf-token` |
| 403 | `origin_not_allowed` | A non-`GET` request came from an origin that is not allowed |
| 404 | `not_found` | The resource does not exist in your tenant (`message` names it, for example `Run not found`) |
| 404 | `route_not_found` | No such endpoint |
| 409 | `run_not_running` | Cancelling a run that has already finished |
| 409 | `run_cancelled` | Retrying a task in a cancelled run |
| 409 | `lease_lost` | A worker reported on a task it no longer holds (see [Complete a task](#complete-a-task)) |
| 409 | `worker_offline` | A worker the API marked offline sent a poll or heartbeat; it must register again |
| 409 | `last_owner` | Removing the workspace's last owner |
| 413 | `definition_too_large` | The workflow definition exceeds `DEFINITION_MAX_BYTES`; `details` is `{ bytes, limit }` |
| 413 | `checkpoint_too_large` | A checkpoint exceeds 256 KiB of JSON |
| 413 | `fst_err_ctp_body_too_large` | The request body exceeds `MAX_PAYLOAD_BYTES` (default 1 MiB) |
| 415 | `fst_err_ctp_invalid_media_type` | The body's `Content-Type` is not supported. Send `application/json` |
| 422 | `invalid_workflow` | The workflow definition failed validation; see [Validation errors](/docs/workflows#validation-errors) |
| 429 | `rate_limited` | A request rate limit was exceeded; `details.scope` is `ip`, `credential` or `tenant` |
| 429 | `auth_rate_limited` | Too many failed authentication attempts from this client address |
| 429 | `quota_exceeded` | A tenant quota was reached; `details` is `{ quota, limit, usage }` |
| 429 | `too_many_streams` | Too many open live streams for the workspace; `details` is `{ limit }` |
| 500 | `internal` | An unexpected server error |
| 503 | `database_unavailable`, `database_timeout` | The database is unreachable or too slow. The response carries `Retry-After: 1` |

Treat 429 and 5xx responses as transient and retry with backoff; the other 4xx responses will fail the same way again. The SDK's `FlowForgeError.transient` follows this rule.

## Rate limits and quotas

### Rate limits

The API applies fixed one-minute windows at several points. Limits are counted per API process, so with N instances the effective ceiling is N times the setting.

| Limit | Setting (default) | Keyed by | Error |
| --- | --- | --- | --- |
| Requests before authentication | `RATE_LIMIT_IP_PER_MINUTE` (6000; `0` disables) | Client IP | `429 rate_limited`, `details.scope: "ip"` |
| Failed authentication attempts | `AUTH_FAILURE_LIMIT` (30) per `AUTH_FAILURE_WINDOW_MS` (60000) | Client IP | `429 auth_rate_limited` |
| Authenticated requests | `RATE_LIMIT_KEY_PER_MINUTE` (1200) | API key, or dashboard user | `429 rate_limited`, `details.scope: "credential"` |
| Authenticated requests | `RATE_LIMIT_TENANT_PER_MINUTE` (6000) | Tenant, across all its credentials | `429 rate_limited`, `details.scope: "tenant"` |

`GET /health` is exempt from the per-IP limit. Once a client address reaches the failed-authentication limit, its requests are refused until the window ends, including requests with a valid key. The client IP is the socket address unless `TRUST_PROXY` says which proxies to trust (see [Operations](/docs/operations)).

Authenticated `/v1` responses carry the budget that is closer to running out (credential or tenant):

```http
x-ratelimit-limit: 1200
x-ratelimit-remaining: 1187
x-ratelimit-reset: 42
```

`x-ratelimit-reset` is the number of seconds until the window resets. `rate_limited`, `auth_rate_limited` and `too_many_streams` responses carry a `Retry-After` header in seconds.

### Tenant quotas

Quotas are per tenant and checked under a lock on the tenant, so concurrent requests cannot overshoot them. Operators change them with `flowforge-admin set-quota <tenant-slug> <quota> <value>`.

| Quota | Default | Enforced when | Effect at the limit |
| --- | --- | --- | --- |
| `max_concurrency` | 256 | Leasing tasks | Tasks stay queued until running tasks finish; no error |
| `max_active_runs` | 500 | Starting a run | `429 quota_exceeded` |
| `max_workflows` | 200 | Registering a new workflow name | `429 quota_exceeded` |
| `max_versions_per_workflow` | 200 | Registering a new version | `429 quota_exceeded` |
| `max_active_workers` | 100 | Registering a worker | `429 quota_exceeded` |

`GET /v1/tenant` (scope `read`) returns the limits and current usage:

```json
{
  "tenant": { "id": "5f0c2a9e-7b1d-4e3a-8c6f-1d2e3f4a5b6c", "slug": "acme", "name": "Acme" },
  "quotas": {
    "max_concurrency": { "limit": 256, "usage": 3 },
    "max_active_runs": { "limit": 500, "usage": 12 },
    "max_workflows": { "limit": 200, "usage": 4 },
    "max_versions_per_workflow": { "limit": 200 },
    "max_active_workers": { "limit": 100, "usage": 2 }
  }
}
```

## Pagination

List endpoints use one of three styles. In every style, a `limit` outside the allowed range is rejected with `400 invalid_request` rather than clamped.

| Style | Endpoints | How to page |
| --- | --- | --- |
| Opaque cursor | `GET /v1/runs`, `GET /v1/attempts` | Pass the response's `nextCursor` as `cursor`. `nextCursor` is `null` on the last page |
| Version cursor | `GET /v1/workflows/{name}/versions` | Same, but the cursor is a version number: the next page holds older versions |
| Event ID | `GET /v1/runs/{id}/events`, `GET /v1/events`, `GET /v1/scheduling/decisions` | `after` (oldest first) or `before` (newest first) an integer ID; see each endpoint |

Some lists are not paginated and return at most a fixed number of rows: workers (200), dead letters (200), a worker's attempts (100), API keys (200), members (500) and task-type statistics (500). `GET /v1/workflows` returns every workflow; the `max_workflows` quota bounds it.

## Tracing

When tracing is enabled on the API (`TRACING_ENABLED=true`), the API reads the W3C `traceparent` header on every request and continues that trace. A run's trace is the one active when the run was submitted. Each leased task carries the run's `traceparent`, and workers send it back as the `traceparent` header on that task's complete, fail and checkpoint calls, so one trace follows a run across every worker and API instance. With tracing off, the header is ignored and leased tasks have `"traceparent": null`. See [Operations](/docs/operations).

## Workflows

See [Workflow definitions](/docs/workflows) for the definition format and validation rules.

### Register a workflow

```http
PUT /v1/workflows
```

Scope `workflows:write`. The body is the workflow definition. The API validates it, applies defaults and stores it as a new immutable version. If an identical definition (after defaults are applied) is already stored as a version of this workflow, the API returns that version instead of creating one.

```sh
curl -X PUT "$FLOWFORGE_API_URL/v1/workflows" \
  -H "Authorization: Bearer $FLOWFORGE_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{"name":"daily-report","tasks":[{"key":"extract","type":"orders.extract"},{"key":"load","type":"report.load","dependsOn":["extract"]}]}'
```

Response: `201 Created` for a new version, `200 OK` when an existing version matched.

```json
{
  "workflowId": "9a8b7c6d-5e4f-4a3b-9c2d-1e0f9a8b7c6d",
  "versionId": "3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f",
  "version": 1,
  "created": true
}
```

Errors: `422 invalid_workflow`, `413 definition_too_large`, `429 quota_exceeded` (`max_workflows` or `max_versions_per_workflow`).

### List workflows

```http
GET /v1/workflows
```

Scope `read`. Returns every workflow in the tenant, ordered by name, with run counts:

```json
{
  "workflows": [
    {
      "id": "9a8b7c6d-5e4f-4a3b-9c2d-1e0f9a8b7c6d",
      "name": "daily-report",
      "description": "Extract orders, clean and enrich them in parallel, then load the report.",
      "latestVersion": 2,
      "updatedAt": "2026-11-06T10:14:58.402Z",
      "runs": 0,
      "lastRunAt": null,
      "lastRunState": null
    }
  ]
}
```

`runs` is the number of runs of any version; `lastRunAt` and `lastRunState` describe the most recent run, or are `null` if there is none.

### Get a workflow

```http
GET /v1/workflows/{name}
```

Scope `read`. Returns the workflow and its latest version, including the stored definition (with defaults applied):

```json
{
  "workflow": {
    "id": "9a8b7c6d-5e4f-4a3b-9c2d-1e0f9a8b7c6d",
    "tenantId": "5f0c2a9e-7b1d-4e3a-8c6f-1d2e3f4a5b6c",
    "name": "daily-report",
    "description": null,
    "latestVersion": 1,
    "createdAt": "2026-11-06T10:14:58.402Z",
    "updatedAt": "2026-11-06T10:14:58.402Z"
  },
  "latest": {
    "id": "3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f",
    "version": 1,
    "checksum": "<sha256 of the canonical definition>",
    "createdAt": "2026-11-06T10:14:58.402Z",
    "definition": { "name": "daily-report", "tasks": [], "defaults": {}, "maxConcurrency": 32 }
  }
}
```

The `definition` above is shortened; the real one contains every task.

### List versions

```http
GET /v1/workflows/{name}/versions?limit=20&cursor=12
```

Scope `read`. Version metadata without definitions, newest first.

| Query | Type | Default | Notes |
| --- | --- | --- | --- |
| `limit` | integer 1–100 | 20 | Page size |
| `cursor` | string | none | A `nextCursor` from a previous page: returns versions older than it |

```json
{
  "versions": [
    {
      "id": "3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f",
      "version": 2,
      "checksum": "<sha256>",
      "createdAt": "2026-11-06T10:20:11.090Z",
      "definitionBytes": 1184
    }
  ],
  "nextCursor": null
}
```

### Get a version

```http
GET /v1/workflows/{name}/versions/{version}
```

Scope `read`. Returns `{ "version": { id, version, checksum, createdAt, definition } }`, or `404 not_found` if the version does not exist.

## Runs

### Start a run

```http
POST /v1/workflows/{name}/runs
```

Scope `runs:write`. Starts a run of the workflow's latest version, or of `version` if given. The body is optional.

| Field | Type | Default | Notes |
| --- | --- | --- | --- |
| `input` | JSON object | `{}` | Run input. Every task's handler receives it as `runInput` |
| `version` | integer ≥ 1 | latest | Workflow version to run |
| `idempotencyKey` | string, 1–200 chars | none | See below |
| `priority` | integer −100 to 100 | 0 | Added to the priority of every task in the run |

```sh
curl -X POST "$FLOWFORGE_API_URL/v1/workflows/daily-report/runs" \
  -H "Authorization: Bearer $FLOWFORGE_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{"input":{"day":"2026-11-01"},"idempotencyKey":"daily-report:2026-11-01"}'
```

Response: `201 Created` with `created: true` for a new run, or `200 OK` with `created: false` when the idempotency key matched an existing run.

```json
{
  "run": {
    "id": "0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b",
    "tenantId": "5f0c2a9e-7b1d-4e3a-8c6f-1d2e3f4a5b6c",
    "workflowId": "9a8b7c6d-5e4f-4a3b-9c2d-1e0f9a8b7c6d",
    "workflowVersionId": "3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f",
    "state": "running",
    "input": { "day": "2026-11-01" },
    "idempotencyKey": "daily-report:2026-11-01",
    "maxConcurrency": 32,
    "priority": 0,
    "createdAt": "2026-11-06T10:15:00.000Z",
    "finishedAt": null,
    "cancelledAt": null,
    "triggeredBy": "api_key:ffk_AbCdEf12",
    "traceContext": null
  },
  "created": true
}
```

**Idempotency keys.** A key is unique per workflow within the tenant. Submitting a key that was already used for that workflow returns the original run, whatever its state, and consumes no quota. The API does not compare the new request's `input`, `version` or `priority` with the original's. Use a key that identifies the business event, such as `daily-report:2026-11-01`, so a client that retries after a timeout cannot start the same work twice. Without a key, every request starts a new run.

Errors: `404 not_found` (workflow or version), `429 quota_exceeded` (`max_active_runs`).

### List runs

```http
GET /v1/runs?state=failed&workflow=daily-report&limit=25
```

Scope `read`.

| Query | Type | Default | Notes |
| --- | --- | --- | --- |
| `state` | `running`, `succeeded`, `failed`, `cancelled` | any | Filter by run state |
| `workflow` | string | any | Filter by workflow name |
| `q` | string, 1–200 chars | none | A run ID (exact match), or the start of an idempotency key |
| `order` | `desc`, `asc` | `desc` | By creation time |
| `limit` | integer 1–100 | 25 | Page size |
| `cursor` | string | none | `nextCursor` from the previous page |

```json
{
  "runs": [
    {
      "id": "0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b",
      "state": "succeeded",
      "workflow": "daily-report",
      "version": 1,
      "priority": 0,
      "createdAt": "2026-11-06T10:15:00.000Z",
      "finishedAt": "2026-11-06T10:15:02.731Z",
      "triggeredBy": "api_key:ffk_AbCdEf12",
      "idempotencyKey": "daily-report:2026-11-01"
    }
  ],
  "nextCursor": null
}
```

### Get a run

```http
GET /v1/runs/{id}
```

Scope `read`. Returns the run (the same fields as when it was started, plus `workflow` and `version`) and a summary of each of its tasks:

```json
{
  "run": {
    "id": "0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b",
    "state": "succeeded",
    "workflow": "daily-report",
    "version": 1,
    "input": { "day": "2026-11-01" },
    "createdAt": "2026-11-06T10:15:00.000Z",
    "finishedAt": "2026-11-06T10:15:02.731Z"
  },
  "tasks": [
    {
      "id": "e1d2c3b4-a5f6-4e7d-8c9b-0a1f2e3d4c5b",
      "key": "extract",
      "type": "orders.extract",
      "state": "succeeded",
      "queue": "default",
      "priority": 0,
      "triggerRule": "all_succeeded",
      "dependsOn": [],
      "attempts": 1,
      "timeoutMs": 300000,
      "workerId": "7f6e5d4c-3b2a-4190-8f7e-6d5c4b3a2f10",
      "enqueuedAt": "2026-11-06T10:15:00.000Z",
      "availableAt": null,
      "startedAt": "2026-11-06T10:15:00.142Z",
      "finishedAt": "2026-11-06T10:15:00.371Z",
      "leaseExpiresAt": null,
      "error": null,
      "output": { "day": "2026-11-01", "orders": [] },
      "outputBytes": 35,
      "outputTruncated": false,
      "createdAt": "2026-11-06T10:15:00.000Z"
    }
  ]
}
```

The `run` object above is shortened. Task summaries leave out inputs and checkpoints, and leave out any output larger than 16 KiB: `output` is then `null` and `outputTruncated` is `true`. Fetch the task with `GET /v1/tasks/{id}` for the full payloads. A task's `error`, when set, is `{ message, code, kind, attempt }`.

Run states are `running`, `succeeded`, `failed` and `cancelled`. Task states are `pending`, `queued`, `running`, `retry_scheduled`, `succeeded`, `failed`, `skipped` and `cancelled`; see [Concepts](/docs/concepts).

### Cancel a run

```http
POST /v1/runs/{id}/cancel
```

Scope `runs:write`. No body. Every task that has not finished (`pending`, `queued`, `running` or `retry_scheduled`) becomes `cancelled`, and the run becomes `cancelled`. Workers running its tasks learn of it at their next heartbeat, and any later report from them fails with `409 lease_lost`. Side effects a handler has already performed are not undone.

```sh
curl -X POST "$FLOWFORGE_API_URL/v1/runs/0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b/cancel" \
  -H "Authorization: Bearer $FLOWFORGE_API_KEY"
```

Returns `{ "run": { … } }` with the updated run. Errors: `404 not_found`, `409 run_not_running`.

## Tasks

### Get a task

```http
GET /v1/tasks/{id}
```

Scope `read`. Returns the full task, including `input`, `output`, `error`, `checkpoint`, `retryPolicy`, `fence` and lease fields, and every attempt in order:

```json
{
  "task": {
    "id": "e1d2c3b4-a5f6-4e7d-8c9b-0a1f2e3d4c5b",
    "runId": "0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b",
    "key": "extract",
    "state": "succeeded",
    "attempts": 1,
    "fence": 1,
    "output": { "day": "2026-11-01", "orders": [] }
  },
  "attempts": [
    {
      "id": "a0b1c2d3-e4f5-4a6b-8c7d-9e0f1a2b3c4d",
      "attempt": 1,
      "fence": 1,
      "workerId": "7f6e5d4c-3b2a-4190-8f7e-6d5c4b3a2f10",
      "workerName": "worker-1",
      "outcome": "succeeded",
      "startedAt": "2026-11-06T10:15:00.142Z",
      "finishedAt": "2026-11-06T10:15:00.371Z",
      "durationMs": 229,
      "error": null
    }
  ]
}
```

The objects above are shortened. Attempt `outcome` is one of `running`, `succeeded`, `failed`, `timed_out`, `lease_expired` or `cancelled`. `workerName` is `null` once retention has removed the worker's record.

### Retry a failed task

```http
POST /v1/tasks/{id}/retry
```

Scope `runs:write`. No body. Re-queues a `failed` task with a fresh retry budget. Skipped tasks that depend on it, directly or through other skipped tasks, are reopened to `pending`, and a `failed` run returns to `running`. The task's dead letter is marked resolved. Returns `{ "task": { … } }`.

Errors: `400 invalid_request` if the task is not `failed`, `409 run_cancelled` if its run was cancelled, `404 not_found`.

### List dead letters

```http
GET /v1/dead-letters
```

Scope `read`. Tasks that failed for good and have not been retried, newest first, at most 200:

```json
{
  "deadLetters": [
    {
      "id": "b2c3d4e5-f6a7-4b8c-9d0e-1f2a3b4c5d6e",
      "taskId": "e1d2c3b4-a5f6-4e7d-8c9b-0a1f2e3d4c5b",
      "runId": "0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b",
      "reason": "retries_exhausted",
      "attempts": 3,
      "lastError": { "message": "connection refused", "code": "error", "kind": "error", "attempt": 3 },
      "createdAt": "2026-11-06T10:16:04.512Z",
      "taskKey": "extract",
      "taskType": "orders.extract"
    }

```

`reason` is `retries_exhausted` or `non_retryable_error`.

## Workers

These endpoints are the worker protocol. The SDK's `createWorker` implements all of it (see [Workers](/docs/workers)); call them directly only if you are writing a worker in another language. All of them require an API key with the `worker` scope.

A worker's lifecycle:

1. Register once, and receive a `workerId`, the lease duration and the heartbeat interval.
2. Long-poll for tasks while it has free capacity.
3. Heartbeat every `heartbeatIntervalMs`, listing the tasks it is running, to renew their leases.
4. Report each task as complete or failed, presenting the task's `fence`; optionally save checkpoints while it runs.
5. Deregister on shutdown.

Every leased attempt has a `fence`, a number that increases each time the task is leased. Reports that present an old fence, come from another worker, or arrive after the lease expired are rejected, so a worker that was paused or cut off cannot overwrite the result of the attempt that replaced it. See [Reliability](/docs/reliability).

### Register a worker

```http
POST /v1/workers
```

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `name` | string, 1–100 chars | yes | Display name |
| `hostname` | string, up to 255 chars | no | |
| `sdkVersion` | string, up to 50 chars | no | |
| `queues` | array of 1–32 queue names | yes | Queues to take tasks from |
| `taskTypes` | array of 1–256 task types | yes | Types the worker has handlers for |
| `capabilities` | array of up to 32 capabilities | no (default `[]`) | Matched against tasks' `requiredCapabilities` |
| `maxConcurrency` | integer 1–256 | yes | |
| `cpu` | number 0.1–1024 | yes | Total CPU the worker offers |
| `memoryMb` | integer 16–4194304 | yes | Total memory the worker offers |

```json
{
  "name": "worker-1",
  "queues": ["default"],
  "taskTypes": ["orders.extract", "orders.clean", "orders.enrich", "report.load", "report.notify"],
  "capabilities": [],
  "maxConcurrency": 4,
  "cpu": 4,
  "memoryMb": 4096
}
```

Response `201 Created`:

```json
{ "workerId": "7f6e5d4c-3b2a-4190-8f7e-6d5c4b3a2f10", "leaseDurationMs": 30000, "heartbeatIntervalMs": 10000 }
```

`leaseDurationMs` and `heartbeatIntervalMs` come from the API settings `LEASE_DURATION_MS` (default 30000) and `WORKER_HEARTBEAT_INTERVAL_MS` (default 10000). Errors: `429 quota_exceeded` (`max_active_workers`).

### Poll for tasks

```http
POST /v1/workers/{id}/poll
```

Leases runnable tasks to the worker. If none is available, the request waits up to `waitMs` for work to arrive before answering with an empty list.

| Field | Type | Default | Notes |
| --- | --- | --- | --- |
| `freeSlots` | integer 0–256 | required | How many more tasks the worker can run now |
| `freeCpu` | number 0–1024 | required | CPU not used by running tasks |
| `freeMemoryMb` | integer 0–4194304 | required | Memory not used by running tasks |
| `waitMs` | integer 0–20000 | 0 | Long-poll wait |

The worker receives only tasks on its queues, of its task types, whose `requiredCapabilities` it has and whose `resources` fit in the free CPU and memory it reported. Run and tenant concurrency limits also apply. Keep one poll in flight per worker: a newer poll for the same worker ID ends an older poll's wait. Set your HTTP client timeout above `waitMs`.

```json
{
  "tasks": [
    {
      "taskId": "e1d2c3b4-a5f6-4e7d-8c9b-0a1f2e3d4c5b",
      "runId": "0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b",
      "key": "extract",
      "type": "orders.extract",
      "attempt": 1,
      "fence": 1,
      "input": {},
      "runInput": { "day": "2026-11-01" },
      "checkpoint": null,
      "timeoutMs": 300000,
      "resources": { "cpu": 1, "memoryMb": 256 },
      "leaseExpiresAt": "2026-11-06T10:15:30.142Z",
      "attemptDeadline": "2026-11-06T10:20:00.142Z",
      "deadlineInMs": 299998,
      "idempotencyKey": "0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b:extract",
      "traceparent": null
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `input` | The task's static `input` from the workflow definition |
| `runInput` | The run's `input` |
| `checkpoint` | The last checkpoint saved by an earlier attempt of this task, or `null` |
| `attempt` | 1 for the first attempt; higher for retries and re-deliveries |
| `fence` | Present it on every report for this attempt |
| `leaseExpiresAt` | When the lease ends unless renewed by a heartbeat |
| `attemptDeadline` | The time the task was leased plus `timeoutMs`; the attempt times out here even if heartbeats continue |
| `deadlineInMs` | Milliseconds from when the API sent the response until `attemptDeadline`. Use this rather than comparing `attemptDeadline` with your own clock |
| `idempotencyKey` | `<runId>:<taskKey>`, the same for every attempt. Pass it to external systems so a re-delivered task does not repeat side effects |
| `traceparent` | The run's W3C trace context, or `null` when tracing is off |

Errors: `404 not_found` (unknown worker), `409 worker_offline`.

### Heartbeat

```http
POST /v1/workers/{id}/heartbeat
```

| Field | Type | Default | Notes |
| --- | --- | --- | --- |
| `active` | array of up to 256 `{ taskId, fence }` | `[]` | The attempts the worker is running |
| `draining` | boolean | `false` | `true` marks the worker `draining`: it keeps its leases but receives no new tasks |

Each listed lease is renewed to `LEASE_DURATION_MS` from now, but never past the attempt deadline.

```json
{
  "renewed": [{ "taskId": "e1d2c3b4-a5f6-4e7d-8c9b-0a1f2e3d4c5b", "leaseExpiresAt": "2026-11-06T10:15:40.150Z" }],
  "revoked": []
}
```

`revoked` lists attempts the worker must stop, as `{ taskId, reason }`. `reason` is `cancelled`, `stale_fence` (the task was leased again), `lease_expired`, `not_found`, or the task's current state if it is no longer running.

A worker that misses heartbeats for `WORKER_OFFLINE_AFTER_MS` (default 60000) is marked offline. Its next heartbeat or poll gets `409 worker_offline`, and it must register again to get a new `workerId`. Leases it held expire on their own, and those tasks are retried according to their retry policy. Draining cannot be undone; register again to receive work.

### Complete a task

```http
POST /v1/tasks/{id}/complete
```

| Field | Type | Notes |
| --- | --- | --- |
| `workerId` | UUID | The worker that holds the lease |
| `fence` | integer ≥ 1 | The fence from the lease |
| `output` | any JSON | Optional; stored as the task's output (`null` if omitted) |

Returns `{ "duplicate": false }`. Resending a completion that was already recorded returns `{ "duplicate": true }`, so retrying after a network error is safe.

If the lease is no longer held, the API answers `409 lease_lost` and records nothing:

```json
{
  "error": {
    "code": "lease_lost",
    "message": "Lease is no longer held (stale_fence)",
    "details": { "reason": "stale_fence", "state": "running" },
    "requestId": "6f1c2b9a-3d4e-4f50-8a61-7b2c3d4e5f60"
  }
}
```

`details.reason` is `stale_fence`, `not_owner`, `lease_expired` or `not_running`. Treat `lease_lost` as final: another attempt owns the outcome.

### Fail a task

```http
POST /v1/tasks/{id}/fail
```

| Field | Type | Notes |
| --- | --- | --- |
| `workerId` | UUID | |
| `fence` | integer ≥ 1 | |
| `error.message` | string, 1–4000 chars | Required |
| `error.code` | string, up to 100 chars | Optional; defaults to `error`, or `non_retryable` when `retryable` is `false` |
| `error.retryable` | boolean | `false` fails the task at once, without retries |

```json
{
  "workerId": "7f6e5d4c-3b2a-4190-8f7e-6d5c4b3a2f10",
  "fence": 1,
  "error": { "message": "upstream returned 503", "code": "upstream_unavailable" }
}
```

Returns `{ "willRetry": true, "duplicate": false }`. `willRetry` is `false` when the retry policy is exhausted or the error was not retryable; the task is then `failed` and dead-lettered. Errors are the same as for completion. If the API already ended this attempt by lease expiry or timeout, the report is acknowledged with `"duplicate": true` and the outcome stands, but the reported error is stored on the attempt as `error.reported` (`message`, `code`, `retryable`; the first report only).

### Save a checkpoint

```http
POST /v1/tasks/{id}/checkpoint
```

| Field | Type | Notes |
| --- | --- | --- |
| `workerId` | UUID | |
| `fence` | integer ≥ 1 | |
| `checkpoint` | any JSON | Up to 256 KiB as JSON text |

Returns `204 No Content`. The next attempt of the task, if there is one, receives the checkpoint in its lease. Errors: `413 checkpoint_too_large`, `409 lease_lost`.

### Deregister a worker

```http
POST /v1/workers/{id}/deregister
```

No body. Marks the worker offline. Tasks it was still running are released at once as failed attempts (outcome `lease_expired`, code `worker_shutdown`) and retried according to their retry policy, without waiting for their leases to expire. Returns `{ "released": 0 }` with the number released.

### List workers

```http
GET /v1/workers
```

Scope `read`. Up to 200 workers, `active` first, then `draining`, then `offline`, most recent heartbeat first. Each has `id`, `name`, `hostname`, `sdkVersion`, `state`, `queues`, `capabilities`, `taskTypes`, `maxConcurrency`, `cpu`, `memoryMb`, `registeredAt`, `lastHeartbeatAt` and `running` (tasks it is running now).

`GET /v1/workers/{id}/attempts` (scope `read`) returns `{ "attempts": [ … ] }`: the worker's 100 most recent attempts, newest first.

## Events

Every run and task state change is recorded as an event in Postgres, in the same transaction as the change. Events have an integer `id` that increases over time within the API's database.

| Event type | `data` fields |
| --- | --- |
| `run.created` | `workflow`, `version`, `tasks`, `triggeredBy` |
| `run.succeeded`, `run.failed` | `durationMs` |
| `run.cancelled` | `by`, `durationMs` |
| `run.reopened` | `by`, `taskId` (after a manual task retry) |
| `task.queued` | `key`, `queue`; plus `manualRetryBy` or `retryOfAttempt` when re-queued |
| `task.started` | `key`, `attempt`, `workerId`, `queuedMs` |
| `task.succeeded` | `key`, `attempt`, `durationMs` |
| `task.retry_scheduled` | `key`, `attempt`, `delayMs`, `kind`, `durationMs` |
| `task.failed` | `key`, `attempt`, `kind`, `durationMs` |
| `task.skipped` | `key` |
| `task.cancelled` | `key`, `from` |
| `task.reopened` | `key` |
| `task.checkpointed` | `key` |
| `worker.registered` | `workerId`, `name`, `queues` |
| `worker.offline` | `workerId` |
| `worker.deregistered` | `workerId`, `released` |

`kind` is `error`, `non_retryable`, `timeout` or `lease_expired`.

### Run events

```http
GET /v1/runs/{id}/events?after=0&limit=200
```

Scope `read`. One run's events, oldest first.

| Query | Type | Default | Notes |
| --- | --- | --- | --- |
| `after` | integer ≥ 0 | 0 | Return events with a larger `id` |
| `limit` | integer 1–500 | 200 | |

```json
{
  "events": [
    {
      "id": 1040,
      "tenantId": "5f0c2a9e-7b1d-4e3a-8c6f-1d2e3f4a5b6c",

      "data": { "workflow": "daily-report", "version": 1, "tasks": 5, "triggeredBy": "api_key:ffk_AbCdEf12" },
```

There is no cursor field: to read the next page, pass the last event's `id` as `after`. A run that does not exist in your workspace returns `404 not_found`; an existing run with no events after `after` returns an empty list.

### Live stream

```http
GET /v1/stream
```

Scope `read`. A [Server-Sent Events](https://html.spec.whatwg.org/multipage/server-sent-events.html) stream of the tenant's events as they are recorded (`Content-Type: text/event-stream`).

| Query or header | Notes |
| --- | --- |
| `runId` (query) | Only send events of this run |
| `after` (query) | Start after this event ID |
| `Last-Event-ID` (header) | Start after this event ID; takes precedence over `after`. Browsers' `EventSource` sends it when reconnecting |

Without `after` or `Last-Event-ID`, the stream starts with events recorded after you connect. The stream opens with `retry: 3000` (reconnect after 3 seconds), then sends each event with its `id` and its type as the SSE event name. `data` is the event as JSON:

```sh
curl -N "$FLOWFORGE_API_URL/v1/stream?runId=0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b" \
  -H "Authorization: Bearer $FLOWFORGE_API_KEY"
```

```http
retry: 3000

id: 1042
event: task.succeeded
data: {"id":1042,"type":"task.succeeded","runId":"0b7c3f5e-2d1a-4c8e-9f6b-7a1d2e3f4a5b","taskId":"e1d2c3b4-a5f6-4e7d-8c9b-0a1f2e3d4c5b","data":{"key":"extract","attempt":1,"durationMs":229},"createdAt":"2026-11-06T10:15:00.371Z"}

: ping
```

- **Heartbeat.** A `: ping` comment line every 15 seconds keeps proxies from closing an idle stream. SSE clients ignore it.
- **Resuming.** Reconnect with `Last-Event-ID` (or `?after=`) set to the last ID you processed, and you receive every event you missed, in order.
- **`reset`.** If you ask to resume from an ID more than 1000 below the newest event's ID, or from an ID ahead of it, the server sends `event: reset` with `data: {"cursor": <id>}` instead of replaying. Reload the state you display from the REST endpoints, then continue; the stream carries on from `cursor`. A `reset` can arrive on a stream filtered by `runId`.
- **Lifetime.** Every 30 seconds an open stream re-checks its credential and closes if the key was revoked or expired, the session ended, the member was removed or the session switched workspace. Reconnecting with a credential that no longer works fails with `401`; after a workspace switch it streams the new workspace. The server also closes each stream after 30 minutes, and the client reconnects.
- **Limit.** Each API process accepts 50 open streams per tenant. More get `429 too_many_streams`.

A client that reconnects without `Last-Event-ID` or `after` starts from the newest event and misses anything recorded while it was disconnected.

## Dashboard endpoints

The dashboard uses these endpoints. They are available to API keys too, except the key management endpoints and `DELETE /v1/members/{userId}`.

### API keys

All three require a signed-in `owner` or `admin`; API keys get `403 forbidden`.

`GET /v1/keys` lists up to 200 keys, newest first, with `id`, `name`, `prefix`, `scopes`, `createdAt`, `lastUsedAt`, `expiresAt`, `revokedAt` and `createdBy` (the creator's email). Secrets are never returned.

`POST /v1/keys` creates a key:

| Field | Type | Notes |
| --- | --- | --- |
| `name` | string, 1–100 chars | |
| `scopes` | array of 1–4 of `read`, `workflows:write`, `runs:write`, `worker` | |
| `expiresInDays` | integer 1–3650 | Optional; without it the key does not expire |

Response `201 Created`. `key` is the full secret, returned only this once:

```json
{
  "key": "ffk_AbCdEf12_<43-character secret>",
  "apiKey": {
    "id": "c3d4e5f6-a7b8-4c9d-8e0f-1a2b3c4d5e6f",
    "name": "nightly-worker",
    "prefix": "ffk_AbCdEf12",
    "scopes": ["worker"],
    "expiresAt": null
  }
}
```

`POST /v1/keys/{id}/revoke` revokes a key at once and returns `{ "apiKey": { "id", "revokedAt" } }`. Revoking a key that is unknown or already revoked gets `404 not_found`.

### Members

`GET /v1/members` (scope `read`) lists up to 500 workspace members with `userId`, `email`, `name`, `avatarUrl`, `role` and `since`.

`DELETE /v1/members/{userId}` removes someone from the workspace and ends their sessions in it; `204` on success. Signed-in owners and admins only (API keys get `403`). Admins can remove members and viewers; removing an owner or admin needs an owner (`403`). Removing the last owner is refused with `409 last_owner`; a user who is not a member gets `404`. API keys the person created are not revoked.

### Attempts

```http
GET /v1/attempts?outcome=failed&limit=50
```

Scope `read`. Task attempts across the tenant, most recently started first.

| Query | Type | Default |
| --- | --- | --- |
| `outcome` | `running`, `succeeded`, `failed`, `timed_out`, `lease_expired`, `cancelled` | any |
| `workerId` | UUID | any |
| `limit` | integer 1–100 | 50 |
| `cursor` | string | none |

Returns `{ "attempts": [ … ], "nextCursor": "…" }`. Each attempt has `id`, `taskId`, `runId`, `attempt`, `outcome`, `startedAt`, `finishedAt`, `durationMs`, `error`, `workerId`, `workerName`, `taskKey` and `taskType`.

### Scheduling

`GET /v1/scheduling/decisions` (scope `read`) lists why each task went to the worker it did, newest first. Query: `before` (integer ID) and `limit` (1–200, default 50). Returns `{ "decisions": [ … ], "nextBefore": … }`. Each decision has `id`, `taskId`, `runId`, `taskKey`, `taskType`, `workerId`, `workerName`, `strategy`, `score` (the task's effective priority when it was chosen), `advisorUsed`, `predictedDurationMs`, `confidence`, `modelVersion` and `createdAt`. This release schedules with the deterministic policy only, so `strategy` is `deterministic`, `advisorUsed` is `false`, and the prediction fields are `null`.

`GET /v1/scheduling/stats` (scope `read`) returns `{ "taskTypes": [ … ] }`: per task type, `taskType`, `samples` (successful attempts), `failures`, `meanDurationMs`, `stddevDurationMs`, `ewmaDurationMs` and `updatedAt`, up to 500 types, most samples first.

### Statistics

`GET /v1/stats/overview` (scope `read`) returns current counts:

| Field | Contents |
| --- | --- |
| `runs` | Run count per state, for example `{ "running": 3, "succeeded": 120 }` |
| `queues` | Per queue and task state (`queued`, `running`, `retry_scheduled`): `{ queue, state, n, oldest }`, where `oldest` is the earliest enqueue time |
| `workers` | Worker count per state |
| `deadLetters` | Unresolved dead letters |
| `generatedAt` | When the numbers were read |

`GET /v1/stats/timeseries?hours=24` (scope `read`; `hours` 1–168, default 24) returns hourly buckets ending with the current hour:

```json
{
  "hours": 24,
  "generatedAt": "2026-11-06T10:20:00.000Z",
  "buckets": [
    {
      "start": "2026-11-06T10:00:00.000Z",
      "runs": { "succeeded": 14, "failed": 1 },
      "attempts": { "succeeded": 70, "failed": 3 },
      "succeededDurationMs": { "p50": 212, "p95": 940 }
    }
  ]
}
```

`runs` counts runs by the hour they finished, `attempts` counts attempts by outcome, and `succeededDurationMs` holds the median and 95th percentile duration of successful attempts, or `null` if there were none.

## Health checks

These are outside `/v1` and need no credential.

`GET /health` returns `{ "status": "ok" }` while the process is up.

`GET /ready` returns `200` with `{ "status": "ready", "database": "ok", "redis": "ok" }` when the API can serve traffic, or `503` with `"status": "not_ready"`. `database` is `ok`, `timeout` or `unavailable`, and `redis` is `ok`, `degraded` or `not_configured`; a degraded Redis adds `redisDetail.lastOkAt` (ISO 8601 time of the last successful round trip, or `null`). The reason is logged by the API, not returned, because the endpoint is public. The endpoint answers within `READY_TIMEOUT_MS` (default 2000). A degraded Redis makes the API not ready only if `READY_REQUIRES_REDIS=true`, because the engine falls back to polling Postgres without it. See [Operations](/docs/operations).
